### 4.2 需要写成明确结论的通用约定

1. 数据库名沿用候选`wardrobe_demo`；表引擎InnoDB、字符集utf8mb4，拟采用前述排序规则。所有字符串外键两侧的类型、长度、字符集和排序规则一致；整数外键两侧均为UNSIGNED，避免建表时才发现不匹配。
2. 除自增ID外，必填业务字段不设置掩盖缺失输入的默认值；`note`默认空字符串、`is_archived`默认0，可空头像/来源/心情/照片/登录态默认NULL。HTTP完整表单仍要求显式字段，数据库默认值不作为缺字段兼容。分类ID、名字和顺序由固定分类数据显式写入。
3. created_at、updated_at均NOT NULL、无数据库自动默认/ON UPDATE，由后端或导入端在写入时显式提供UTC DATETIME(3)；创建时相同，更新只改updated_at。连接时区由阶段3设置UTC。本阶段只读取现有会话时区，不修改实例或会话设置。
4. wear_date使用DATE，按Asia/Shanghai自然日解释；DATE读取为`YYYY-MM-DD`字符串，禁止先转JS Date再平移日期。接口系统时间使用带Z的ISO字符串；正式当天由服务端确定，固定2026-11-06仅为样例核验参数。
5. 账号trim后只允许4～20位ASCII字母、数字、下划线，统一小写；密码不trim，8～64字符。沿用异步scrypt：16字节随机盐、64字节结果、N=16384/r=8/p=1，编码包含算法与参数，保存字段上限255；不得把密码或派生串放进公开样例。
6. 登录返回32字节随机令牌的base64url编码，数据库只保存SHA-256十六进制摘要和UTC到期时间；摘要/到期时间同时为NULL或同时非NULL。新登录覆盖旧值，退出同时清空，不另设会话表。
7. 正式主实体ID和所有数量在JSON中是整数，不是CLO字符串或数字字符串；INT UNSIGNED范围可由JS安全表示。分类ID仍是固定字符串，API中的categoryId不能统一改成整数。
8. 单行文本trim，备注保留换行；字段长度按Unicode字符计，与数据库字符长度语义对齐。空备注为`""`，可选心情为空转为null，无来源/无照片为null，不使用`"null"`、空数组代替或虚构图片。

上述细化执行时写入最终设计并与总方案同步。若发现已有明确选择不同，先列出依据与影响，再作一处一致修改，不保留两套互相矛盾的规则。

### 4.3 约束、索引及关系核对

执行时给所有外键、唯一约束及CHECK固定可读名称，错误处理按约束身份映射，不能仅凭“任何重复键错误”认定日记日期冲突。

| 规则 | 数据库职责 | 业务入口/事务职责 |
| --- | --- | --- |
| 账号唯一 | username唯一索引 | 先规范化；已知唯一冲突映射USERNAME_TAKEN |
| 登录态成对 | 摘要唯一且可空；CHECK保证摘要和到期时间同时空/非空 | 安全生成、过期判断、覆盖及退出；不返回摘要 |
| 每人每天一篇 | UNIQUE(user_id,wear_date) | 日期真实且不晚于上海当天；编辑排除自身；冲突409并保留草稿 |
| 衣物去重/位置唯一 | 两张明细的复合PK与父ID+sort_order唯一；CHECK顺序>=1 | 1～20件、数组去重、顺序连续1～n；事务替换，不用触发器统计子行数 |
| 基本值域 | CHECK归档0/1、季节8个约定值、分类/明细正序 | 格式、长度、分类合法性及页面可选范围在请求边界一次校验 |
| 引用与用户归属 | FK只保证记录存在 | 当前身份来自认证；父记录查询带user_id；一次校验所选衣物均归当前用户，不接受body.userId |
| 归档保留/历史独立 | 衣物、搭配不物理删；日记独立关联衣物 | 修改搭配只写outfit_items，不改diary_items；当前名称图片不做快照 |
| 图片与未来日期 | 不让外部URL/TMP/blob进入持久记录；不以含当前日期函数的CHECK代替业务判断 | 图片目录归属、存在性和实际格式；服务端日历日期校验 |

必要索引沿用总方案：

- clothes：`idx_clothes_user_archived_id(user_id,is_archived,id)`、`idx_clothes_category(category_id)`。
- outfits：`idx_outfits_user_archived_id(user_id,is_archived,id)`。
- outfit_items：`idx_outfit_items_clothing(clothing_id,outfit_id)`；diary_items：`idx_diary_items_clothing(clothing_id,diary_id)`。
- diaries：用户日期唯一索引兼顾月查询；`idx_diaries_source_outfit(source_outfit_id)`。users和categories采用前述唯一索引。

最终索引表列出名称、列顺序、唯一性和用途，检查外键需要的索引已由PK/UNIQUE/上述索引覆盖，不额外建立重复前缀索引或为模糊搜索提前优化。

所有FK的ON UPDATE保持RESTRICT；ON DELETE仅`diary_items.diary_id → diaries.id`使用CASCADE，其余RESTRICT。日记删除不删图片、衣物、来源搭配；不新增软删除日记或账号删除接口。

事务说明至少覆盖：搭配主表+明细一起新增/替换；日记主表+独立明细一起新增/替换；删除日记及级联明细。图片写磁盘不属于数据库事务，用户隔离也不是靠FK自动完成。

### 4.4 ER图、页面和字段的一致性检查

以7张表为ER图实体；标清用户一对多、分类一对多、两种明细、日记可选来源。ER图的“至少1件”是业务保存规则，FK本身不能保证父表一定有明细。字段表的可空来源必须与ER图可选基数、接口null一致。

建立“页面→接口→表/字段→规则”表：衣橱3页关联clothes/categories，搭配3页关联outfits/outfit_items，日记3页关联diaries/diary_items，统计1页读取现有表；认证资料另计users。不能为统计页强加第8张表，也不能为满足10页重复计算新增/编辑模式。

### 5.3 协议、字段和空值的定稿要求

- 除A01、A02、A09外均要求Bearer令牌，包括分类和图片；不把其他用户记录区分为“存在但无权”，统一404。图片读取从当前用户目录推导位置，不接收任意userId/文件系统路径。
- 成功统一使用data包裹，例如`{"data":{"items":[]}}`；创建201、其余200；A08成功返回真实图片二进制及正确Content-Type，不套JSON。错误格式例如`{"error":{"code":"INVALID_INPUT","message":"参数无效","details":{"fields":{"name":"请填写名称"}}}}`，无必要信息时不带details；不把错误包在200。此处仅示意外层格式，各接口仍须给出完整字段示例。
- 列表`items/page/pageSize/total`；page默认1，pageSize默认12、范围1～50；超过末页为空items但保留真实total。月历返回`month/items`，不硬套分页。categories返回items，facets返回去重颜色/场景数组。
- 默认主列表id降序；日记历史wearDate降序；月历日期升序；明细sort_order升序；榜单次数降序/整数ID升序；未穿列表ID升序。分页排序必须稳定，不开放任意SQL排序参数。
- `keyword`最长40、字面子串、忽略大小写；转义LIKE的`%`、`_`和转义字符本身，参数绑定。颜色/场景按trim后完整文字精确匹配，不推测同义色；`archived=active|archived|all`默认active，筛选选项只随该用户和归档范围变化，不随keyword收窄。
- 衣物存储season允许8个值，查询season只接受春/夏/秋/冬单季；例如秋匹配秋/春秋/秋冬/四季。其他单季在文档写全映射；“全部”不传该参数。
- 正整数ID不能接收原型字符串/TMP；clothingIds是1～20个去重、有序整数。完整PUT要求全部可编辑字段，可空项显式null，备注显式空字符串；归档只走PATCH的boolean，不允许改owner。
- `User`不返回密码、哈希、令牌摘要；LoginResult才返回原令牌与expiresAt。imagePath是持久相对路径，imageUrl临时按当前服务地址派生，不存数据库。
- 无照片/头像的path、url同为null；lastWornDate无记录为null，wearCount为0；D02无当日记录为`data.diary=null`，D03不存在为404。未知ID与无记录日期不能共用一套null语义。

校验字段逐一与总方案3.5对照：账号4～20、密码8～64、昵称1～20、名称1～40、颜色和场景1～20、衣物/搭配备注0～500、日记文字0～1000、心情null或1～12、有效DATE、JPEG/PNG单图不大于5MiB。日期是日期，系统时间是ISO UTC字符串，不能混用。

### 5.4 日记、图片与统计的关键语义

日记新增/编辑必须明确实际clothingIds，不从来源搭配重新生成明细。来源归当前用户即可，可为归档搭配；归档衣物可带标记查看和选择，默认选择列表仍为active。编辑实际清单不强制清空来源，也不强制与来源一致。

DATE_OCCUPIED使用409，details含wearDate和当前用户existingDiaryId；编辑排除自身，并由数据库唯一约束处理竞争，禁止静默覆盖/合并。非法日期和未来日期为400；事务失败不部分保存或重排旧数据。

图片流程为A07鉴权上传→返回稳定imagePath→表单提交路径→业务记录引用→A08鉴权下载。服务端校验JPEG/PNG内容、解码及5MiB限制，保存UUID文件名到`server/uploads/users/<整数用户ID>/`。小程序带Authorization下载后使用临时文件显示，TMP、blob、wx临时路径不能写入持久数据。替换、取消或删除日记不立即删除磁盘文件；不新增图片会话表、自动清理或缓存系统。上传和鉴权读取的真正可用性留阶段3验证。

统计从当前用户日记实时查询，明确以下范围，不维护计数字段：

| 指标 | 契约应说明的计算范围 |
| --- | --- |
| activeClothesCount / categoryDistribution | 当前用户未归档衣物；7类固定顺序，空类返回0 |
| monthDiaryDays | 所选月份日记数量，月初闭区间至下月初开区间；一篇有多件衣物仍只计1天 |
| wearCount / lastWornDate | 包含该衣物的日记篇数 / 最大wearDate；衣物归档不抹去历史 |
| mostWorn | 截至服务器asOf的累计记录，只取未归档且次数>0的Top5；次数降序、ID升序 |
| notWornRecently | 未归档衣物在[asOf减29天,asOf]无关联记录，含首尾和从未穿者；独立分页 |

切换month只变月天数，榜单及30天窗口不随月份回溯。接口不提供任意asOf参数；样例核验固定日期是内部核对条件，不是公共业务能力。

### 6.2 实际执行时允许的只读核对

下列SQL只是后续人工/客户端核对清单，本轮未执行。不把查询清单存为`schema.sql`。查询版本后再使用该版本支持的语句；若实际是MariaDB或不满足目标MySQL版本，明确记录产品差异，不套用MySQL8结论。

```sql
SELECT VERSION() AS server_version, @@version_comment AS version_comment,
       @@hostname AS server_host, @@port AS server_port;
SELECT CURRENT_USER() AS authenticated_account, USER() AS connection_identity,
       DATABASE() AS selected_database, CURRENT_ROLE() AS active_roles;
SELECT @@default_storage_engine AS default_engine,
       @@character_set_server AS server_charset,
       @@collation_server AS server_collation,
       @@session.time_zone AS session_time_zone,
       @@global.time_zone AS global_time_zone,
       @@system_time_zone AS system_time_zone,
       @@session.sql_mode AS session_sql_mode,
       @@session.foreign_key_checks AS session_fk_checks;
SHOW ENGINES;
SHOW COLLATION WHERE Collation = 'utf8mb4_0900_as_cs';
SHOW GRANTS FOR CURRENT_USER();
SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM INFORMATION_SCHEMA.SCHEMATA
WHERE SCHEMA_NAME = 'wardrobe_demo';
SELECT TABLE_NAME, TABLE_TYPE, ENGINE
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = 'wardrobe_demo'
ORDER BY TABLE_NAME;
```

解释规则：

- `VERSION()`才是当前连接的服务端版本证据；客户端`--version`单独记载。hostname/port用于识别实际目标，不能用文件版本或Windows服务状态替代。
- 对MySQL 8.0目标，确认InnoDB为YES/DEFAULT、utf8mb4及选定排序规则存在、STRICT相关sql_mode及foreign_key_checks状态。CHECK按版本支持和建表时的ENFORCED定义核对，不查询其他数据库产品的CHECK开关；新表的实际ENFORCED元数据留P2-02核对。缺少必要能力/配置时记录为阻塞，不改现有全局设置；连接UTC设置属于后续工程连接配置。
- 服务端8.0.16之前的CHECK不会按现有目标执行；即使版本满足，也只能记为“版本/配置具备设计能力”，不能记为“非法写入被拒绝已验证”。[MySQL官方CHECK约束说明](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)
- `SHOW GRANTS FOR CURRENT_USER()`检查当前认证账号授权。若有角色，结合CURRENT_ROLE及针对已确认激活角色的SHOW GRANTS USING展开权限，并核对目标库的限制/撤销项；没有展开或无法判断时标为待核对，不推断“ALL足够”。不读取mysql.user、SHOW CREATE USER或认证哈希。[MySQL官方SHOW GRANTS说明](https://dev.mysql.com/doc/refman/8.0/en/show-grants.html)
- INFORMATION_SCHEMA查询只针对项目拟名库；没返回行可能是不存在或当前账号不可见，必须结合授权判断，不能据此宣布“空库已确认”。若可见同名库已有对象，记录清单和归属待核对，禁止自动清空或重建。
- 不要求给当前用户PROCESS、FILE、SUPER、GRANT OPTION等无关权限来完成本项目核对，不读取其他业务库的数据。

导入只准备24张衣物主图和1张DIA004照片，共25个业务图片引用；搭配预览板、来源网页、风格参考不导入。P2-03映射为`users/<实际用户ID>/<服务器生成文件名>`，物理根为未来`server/uploads/`，不改原assets文件或其清单。目录准备不等于Express工程创建，鉴权HTTP访问留阶段3。

sourceOutfitId=null表示直接补记；photoPath=null合法且无文件复制。空心情按null、空文字按空字符串；现样例未出现这两类空值，P2-03/正式测试以独立验证输入覆盖，不改写原始样例凑用例。原始用户ID、TMP和blob值不能成为数据库外键或持久路径。

沿用“项目专用空库、已有业务数据则停止”的导入前置条件，不清空、不覆盖、不用INSERT IGNORE吞掉差异。数据库导入一个事务，源文件先核对存在；图片复制不随数据库事务回滚，失败后的文件供人工核对，不引入自动删除任务。P2-01只交接这些条件，实际脚本到P2-03编写。
