## 1. 目标、依据与边界

依据项目《详细设计与实施方案》第3、8、9节、《执行计划》及现有演示JSON，完成衣橱、搭配、日记、我的四入口的静态可点击原型，用于检查布局、图片、导航和只读浏览。正式项目继续采用原生微信小程序、Express及MySQL；HTML原型用于验证界面与交互。

本计划沿用frontend-skill中的应用界面原则：清晰的内容层级、单品图主导、克制的界面颜色和装饰，且以项目已确定的视觉约定为准。

### 1.1 本阶段做到什么

- 四入口切换、当前入口标记、各页独立滚动及会话内浏览状态保留。
- 衣橱展示24件真实单品，支持名称搜索、分类筛选、只读快速预览。
- 搭配展示8套真实组合，支持场景筛选、只读完整组合预览。
- 日记显示月历，支持月份切换、日期选择及当天只读摘要，能查看2026年10月和11月样例。
- 我的显示明确的演示用户资料、样例总量和可展开的数据说明。
- 明确处理数据加载、筛选无结果、无记录日期和图片读取失败。

## 3. 四入口的内容与滚动设计

### 3.1 共用页面结构

视图从上到下为：当前页面名称与“演示原型 · 示例数据”小标识 → 当前入口内容 → 底部四入口导航。

页头和底部导航不随内容滚动，中间区域由当前入口独立滚动。衣橱、搭配、日记、我的各保留一个页面容器，切换显示状态，不反复重建整个应用。因此，切回衣橱仍保留查询条件及浏览位置，切回日记保留月份和选中日期。

不增加营销横幅、每日推荐、天气、会员等区域。常用操作位于内容附近，真实图片进入衣橱首屏，日历进入日记首屏。

### 3.2 衣橱

**首屏与内容顺序**

1. 页头“衣橱”，数量说明为“共24件单品”；搜索或分类变化时另显示“找到N件”。
2. 名称搜索框，提示“搜索衣物名称”；输入非空时出现清除按钮。
3. 横向分类栏：“全部”及7个分类，按categories.sortOrder排列，当前分类以强调色和下划线标记。
4. 两列单品网格：完整主图、名称，辅以颜色或分类文字；名称最多显示两行。
5. 内容底部保留足够留白，最后一件不被导航遮住。

**数据与交互**

只读展示clothes，默认显示全部24件；名称按子串匹配，分类按categoryId匹配，两个条件同时生效。输入时立即更新24件样例的筛选结果，不增加防抖、分页或远程请求。分类数量从数据计算，不写死在HTML。

本阶段列表保留样例数组顺序，便于与素材核对，不标注“最新”；正式业务接口接入时再遵循总方案的接口排序。所有数据运算生成展示结果，不对源数组原地排序或修改字段。

点击单品打开只读快速预览：主图、名称、分类、颜色、季节和已有备注。预览内不放编辑、归档或记录穿着操作。长图片及文字在预览内容区滚动，关闭后回到原列表位置。

**长内容与空态**

分类栏只横向滚动，衣物网格只纵向滚动，整个页面不出现横向溢出。筛选无结果时显示“没有找到匹配的衣物”和“清除筛选”；清除同时重置名称与分类。源数据未成功加载时显示加载错误，不用空数组伪装成空衣橱。

### 3.3 搭配

**首屏与内容顺序**

1. 页头“搭配”，显示“8套示例搭配”。
2. 场景切换：全部、校园、休闲、出游，选项从实际数据生成。
3. 搭配列表，采用单列组合行：左侧2×2真实单品缩略预览，右侧名称、场景、单品数量。
4. 超过4件时，在预览外或固定角落显示“共5件/共6件”，不让第5、6件看似丢失。

**数据与交互**

使用outfits[].clothingIds按顺序关联clothes。列表只展示前4张图，点组合行打开只读预览，显示名称、场景、备注及全部有序单品；按每件实际imagePath显示，不使用预先拼好的搭配总览图。

预览中的单品只读，不继续建立多层详情跳转；本阶段只有一个预览层。OUT007“小花半裙计划”保留原名和备注；保存的搭配数量不等于穿着次数，不给此组合伪造已穿记录。

**长内容与空态**

8套列表纵向滚动，场景切换后列表滚回顶部。每个场景都有样例，无需额外篡改源数据制造空场景；筛选结果为空的通用提示仅在实际出现时使用。6件组合预览内容独立滚动，标题和关闭按钮保持可见。

### 3.4 日记

**首屏与内容顺序**

1. 页头“日记”。
2. 月份行：上月按钮、明确年月、下月按钮，下一行显示“本月记录N天”。
3. 周一至周日的7列星期标题。
4. 固定6行、42个位置的日历；当前月日期可选，邻月位置留空且不可点击。有日记的日期加圆点，选中日期使用强调色底。
5. 选中日期摘要：日期、场景、心情、文字和当次衣物缩略图；有附图时额外完整显示该图及参考图说明。

**月份与日期规则**

- 上下月按自然月切换，年份随之变化；不限死为两个月，但必须验证2026年10月和11月。
- 切换到一个月份后，优先选中该月最早一篇日记日期；该月无记录时选月初。这个规则仅用于月份变化；tab切换保留原选择。
- 第一次打开使用第2.2节的最新示例日期；因此初次选中11月5日，手动从10月切回11月时按规则选中11月1日。
- 选择日期只改变只读摘要，不新增记录；无记录日期显示“这一天暂无穿搭记录”。不显示尚未实现的“记一笔”。
- 在只读原型中，未来日期也只是可查看的空日期，不提供写入行为；正式录入的日期边界仍按总方案实施。

**数据对应**

按wearDate取当月日记并计算数量；选中日按日期精确匹配。摘要衣物必须来自该diary.clothingIds，不能改用来源搭配的当前清单。照片严格使用photoPath；为空就显示当次衣物，不补真人照片。

日历按年份、月份和天数计算，只把YYYY-MM-DD作为自然日键使用；月份运算可用UTC构造取星期，不把源wearDate转换为带时区的显示日期。10月16日附图旁显示“同款穿着参考”，其虚构样例身份在数据说明中解释。

**长内容与空态**

日历和下方摘要在日记页同一个纵向滚动区域内；月历固定6行减少切月时上下跳动。切月后滚回页内顶部，选日期不自动把日历滚走。无记录月份仍有完整日历、0天说明及选日空态，不能显示加载错误。

### 3.5 我的

**首屏与内容顺序**

1. 页头“我的”。
2. 演示身份区：头像使用昵称首字“小”的纯文字占位，显示“小夏的演示衣橱”，附“演示用户”标记。
3. 一行样例总量：24件衣物、8套搭配、12篇日记，直接从源数组计算；使用简洁文字与分隔线，不堆叠成多个仪表盘卡片。
4. “数据说明”展开项，说明记录是虚构样例、图片来源为CHERRYKOKO和Pexels、附图为同款穿着参考、当前原型只供浏览。

“数据说明”可展开/收起。总量只是只读摘要，不伪装成独立统计页入口；不显示账号密码、真实头像、编辑资料或退出登录按钮。后续个人资料与详细统计接入时再添加相应入口。

内容超出高度时页内滚动；昵称按最多两行布局，不能挤压头像或越过容器边界。

下表是P1-01实际控件清单；实施时不得存在未登记且无反馈的可点击外观。后续功能按第1.2节处理，不在本阶段显示“开发中”按钮集合。

| 控件 | 点击/输入后的行为 | 读取或更新 | 本阶段反馈 |
| --- | --- | --- | --- |
| 四个底部入口 | 显示对应视图并更新页头 | activeTab；各页原状态保持 | 当前入口强调，其他视图隐藏 |
| 已选中的底部入口 | 保持当前视图及位置 | 不改数据 | 不重复初始化，不弹无意义提示 |

| 我的“数据说明” | 展开或收起说明 | aboutExpanded | 展开指示与可见内容一致 |
| 数据加载失败后的“重新加载” | 用户主动再次读取同一个JSON | 加载状态 | 成功显示内容，失败继续提示；无自动循环重试 |

衣物和搭配预览是一个可复用的只读弹层容器：同一时间只显示一个；关闭按钮至少44px点击区域；内容独立滚动；关闭后焦点回到原触发控件。可以使用原生dialog组织语义和关闭行为，具体只读内容由当前preview类型决定。

搜索清除与“清除筛选”行为不同，不能共用一个含糊的清空逻辑。所有筛选和日期切换仅修改内存视图状态，不写入JSON、localStorage或sessionStorage。

## 5. 视觉与响应式实施约定

### 5.1 内容与交互主张

视觉主张：暖白背景、玫瑰色操作强调、真实单品图和轻量分隔，呈现韩系日常衣橱。

内容主张：衣橱首先看衣服，搭配首先看组合，日记首先看日期，我的首先识别演示身份；每个入口有一个清晰的主体。

交互主张：入口和筛选即时反馈；只读预览以轻量弹层呈现；月份选择与日期标记联动。使用短过渡解释状态，不做滚动特效、自动轮播或装饰性入场动画。

### 5.2 样式值与尺度

| 项目 | 本阶段取值 |
| --- | --- |
| 背景 | 页面#FAF8F5，表面#FFFFFF，分隔线#E8E2E3 |
| 文字 | 主文字#2F2D32，次文字#6D6670 |
| 强调 | #A34F69；浅选中底#F6E7ED；避免为每个入口增加不同主题色 |
| 字体 | 系统中文字体，使用系统默认及PingFang SC、Microsoft YaHei等字体回退；不请求公网字体 |
| 浏览器字号 | 页标题22px，区块标题16px，正文14～15px，辅助12px；这是总方案rpx尺度在约375px视口下的原型对应值 |
| 主要间距 | 页面左右14px，衣物列间10px，区块间16～20px；文字行高约1.5 |
| 页面框架 | 移动宽度100%；宽屏预览内容最大430px居中，外围使用安静纯色，不制作装饰手机外框 |
| 页头/导航 | 页头约56px，底部导航约64px并叠加安全区留白；每个入口点击区域不少于44px高 |
| 衣物图片 | 容器4:5，等比完整显示；使用contain，保留背景；不使用cover裁掉衣物 |
| 搭配缩略图 | 2×2等大格，每格contain；数量标记不遮挡关键衣物轮廓 |
| 预览 | 移动端底部面板，最大约82%可视高度；标题和关闭区固定，内容区滚动；图片完整展示 |
| 动效 | 约160～200ms的颜色/透明度/弹层过渡；遵循系统减少动态效果设置 |

375px宽时，左右各14px、列间10px，单品列宽约168.5px；430px宽时约196px。图片容器随列宽变化，文字字号保持可读，不把整页连同文字作为图片等比缩放。

### 5.3 必查布局点

- 在375×812和430×932两个视口检查四个入口，不用只看宽屏桌面效果。
- 衣橱首屏能直接看到完整单品主图；名称允许两行，颜色文字可换行；卡片不固定为不足以容纳文字的高度。
- “灰色细格纹直筒半裙”等长名称和“藏蓝与米白色”等多色文字不横向溢出。
- 列表和弹层都能滚到末尾；底部导航不能覆盖最后一项或日记末尾文字。
- 搜索获得焦点、键盘出现时仍可看见输入和结果；导航由应用布局定位，避免脱离可视区域后挡住内容。
- 分类栏的横向滚动只限该栏，整页不能被拉出水平空白。

### 6.2 地址解析规则

固定静态服务根目录为：`Z:\outfit\personal-wardrobe`，不能只把prototype子目录作为根目录。

| 资源 | 本地HTTP地址 | 解析方法 |
| --- | --- | --- |
| 入口 | `http://127.0.0.1:4173/prototype/` | 静态服务自动读取prototype/index.html |
| CSS/JS | `/prototype/styles.css`、`/prototype/app.js` | HTML同目录相对引用 |
| 数据 | `/data/demo-data.json` | 以模块的上级目录为项目基准，解析data/demo-data.json |
| CLO001图片 | `/assets/clothes/clothing-001.jpg` | 以项目基准解析源imagePath，不额外添加prototype/ |
| 日记参考图 | `/assets/diaries/diary-004.jpg` | 同样解析photoPath |

不把Windows磁盘路径直接写进浏览器image.src，也不直接用文档当前位置解析`assets/...`，否则会误指向`/prototype/assets/...`。项目位置变化只需调整静态服务根目录，源JSON中的相对路径保持原样。

### 6.3 拟用启动方式

本机已核对存在以下Python解释器，其标准库http.server帮助支持port、bind和directory参数。实施时先确认4173端口可用，再在PowerShell运行以下命令；本轮仅核对了帮助，没有启动此服务：

```powershell
& 'C:\Users\NoBugMachine-v2\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -m http.server 4173 --bind 127.0.0.1 --directory 'Z:\outfit\personal-wardrobe'
```

然后通过上表入口URL打开原型，不以file://直接打开HTML，因为数据读取依赖HTTP同源访问。结束预览用终端Ctrl+C停止服务。该服务仅提供静态文件，不是项目的Express业务后端，不连接MySQL。

4173是计划端口，当前未确认占用状态。若实施时已被占用，则选择可用端口并同步记录预览地址，不关闭未知进程。这里使用现有解释器，不新增Python第三方依赖；正式业务技术栈保持不变。

### 6.4 一次加载与数据来源

初始化读取demo-data.json一次，创建衣物ID索引及日记日期索引，按关联数组查找图片和文字。4个入口都从这一份只读源数据派生内容；demo-summary.json只作为验收基线，不在运行时再读取并混合出第二套数量。

数据进入后，分别计算分类数量、场景选项、月份记录数和我的总量。筛选只生成视图数组；组合和日记保留原clothingIds顺序。不要为了显示某种空态删除、清空或改写原始JSON。

数据读取失败时，保留共用导航和明确错误，数据依赖的区域不显示虚构默认数量；用户可手动重新加载。单张图片失败时保留该项名称和占位框并显示“图片读取失败”，不替换无关照片或悄悄隐藏单品。
