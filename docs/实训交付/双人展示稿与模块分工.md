# 个人衣橱与穿搭日记：双人展示稿与模块分工

适用场景：微信开发者工具本地演示，建议7～9分钟。甲、乙替换为两位同学姓名。本稿中的分工是建议展示与后续维护分工；正式报告的真实开发贡献由本人按事实填写，不用本稿倒推或虚构开发经历。界面数值以演示时实际结果为准。

| 人员 | 主讲及建议负责模块 | 时间 | 为什么这样分 |

## 二、开始前准备（不在台上念）

1. 启动本机MySQL及server后端，在微信开发者工具打开现有miniprogram项目。默认API为http://127.0.0.1:3000/api；工具服务端口不必开启。
2. 用zyyuan登录，密码只在本机输入，不在讲稿、投屏终端或幻灯片展示。首次准备的数据为24件衣物、8套搭配、12篇日记；若后来新增了数据，数量会变化，不为对齐数字清库。
3. 日历预先熟悉2026年10月和11月：10月9篇、11月3篇；10月16日有照片，11月5日可看无照片的记录。这些是虚构演示数据，不代表图片人物的真实生活。
4. 甲准备一张本机图片，可使用Z:/outfit/personal-wardrobe/assets/clothes/clothing-001.jpg。现场新增名称用“答辩演示针织”；搭配用“答辩演示搭配”。同名可出现，优先使用本次创建的记录，不误操作原样例。
5. 乙新增日记选择服务器当天或一个过去的空日期。若当天已有记录，就查看/编辑原篇或换过去空日；不覆盖、不调整系统日期、不选择未来日期。只删除本次明确创建的演示日记。
6. 甲操作到搭配详情后将控制权交乙，乙继续同一套搭配。若只有一台电脑，甲讲解时自己操作，乙上场后接鼠标；避免一人讲话、另一人提前翻页。

## 三、可以直接念的展示稿

### 甲：1. 开场与项目背景（约40秒）

【页面：登录后衣橱首页】

老师好，我们展示的项目是“个人衣橱与穿搭日记”微信小程序。我是甲同学，接下来由我介绍账号、衣橱和搭配模块；乙同学介绍穿搭日记、统计，以及关键数据设计。

这个项目面向日常整理衣物和记录穿搭的用户。它解决三个具体问题：衣服多了以后不容易找到，搭配想法不容易保存，也难以回顾哪些衣物经常穿、哪些长期闲置。

我们把主要入口分为衣橱、搭配、日记和我的。前端采用原生微信小程序和JavaScript，后端使用Node.js Express，数据库使用MySQL，目前用于本地演示。

### 甲：2. 账号与衣橱（约1分30秒）

【操作：短暂展示我的页，再回衣橱】

账号登录后，系统根据当前身份访问本人的资料和业务数据。图片也通过登录身份读取，界面使用临时下载路径显示，真正保存的是后端的稳定图片路径。

【操作：搜索“针织”，演示一个分类或颜色/季节筛选，然后清除筛选】

这里是衣橱。每件衣物展示完整单品图，可以按照名称、分类、颜色、季节和归档状态查找。分类用来整理衣物，归档则用于暂时不想放在常用列表里的单品。

【操作：新增衣物，选择图片，填名称、分类、颜色、季节及简短备注，保存】

新增衣物先上传图片，再保存衣物资料。这里的资料实际写入MySQL，所以重新进入页面仍能读取，并不是只在当前页面放一个演示对象。

【操作：打开详情，展示编辑及归档按钮；时间允许时归档后恢复】

详情里可以修改资料，还能看到穿着次数、最近穿着日期以及关联搭配和日记。我们采用归档而不是直接删除衣物，目的是保留它在过去搭配和日记中的关系。

### 甲：3. 保存搭配（约1分20秒）

【操作：搭配→新增→选择2～3件衣物，其中包含本次新增单品；调整顺序，保存“答辩演示搭配”】

搭配模块将多件已有衣物组合保存。选择器支持筛选和多选，切换筛选条件不会把已经选中的衣物清空。同一套搭配不能重复选择同一件衣物，可以移除单品，也可以通过上移、下移调整顺序。

保存时，搭配资料和全部衣物关联在同一个事务里完成，避免出现只保存了搭配名称、组合却只写入一半的情况。

【操作：打开刚保存的详情，指出完整清单】

列表用前几件单品作预览，详情保留全部衣物和实际顺序。保存搭配本身不代表穿过，只有记录成日记以后才参与穿着统计。

接下来请乙同学沿着这套搭配，展示记录穿着和统计过程。

### 乙：4. 从搭配记录日记（约1分10秒）

【操作：搭配详情→记录穿着，查看预填衣物和场景】

大家好，我是乙同学。这是从搭配记录穿着的入口。系统将当前搭配的衣物和场景复制到日记草稿，用户还可以调整实际穿着内容。进入表单只是预填，并不会立即产生记录。

【操作：选合法空日期，填简短心情和文字，照片可选，保存】

日记记录穿着日期、场景、心情、文字、实际衣物和可选照片。照片不是必填项，没有照片时照样能查看本次穿着的单品。

这里有两个日期规则：不能记录未来日期，同一用户同一天最多一篇。数据库用用户和日期的唯一约束保证这一点；遇到已有记录时，页面会提示查看或编辑，不静默覆盖。

### 乙：5. 日历、直接补记与历史独立（约1分20秒）

【操作：回日历，找到刚保存的日期，再切2026年10月或11月】

日历上的标记来自真实日记记录，切换月份可以回顾过去穿搭。除了从搭配进入，选择过去的空日期也能直接选衣补记，不要求先建立一套搭配。

【操作：10月16日日记看附图；再打开11月5日无照片记录，时间不足只展示其中一篇】

这里有带照片和不带照片的两种记录。衣物或来源搭配已经归档时，过去的日记仍保留关联。

【操作：回本次“答辩演示搭配”，移除其中一件并保存；再打开本次新日记】

这个项目的重要规则是历史记录独立。修改搭配后，之前的日记仍保留当时保存的衣物集合和顺序。来源搭配只是说明记录从哪里开始，不能用它的最新清单替代历史日记。

不过衣物名称、图片仍读取当前属性，我们没有增加衣物属性的历史版本，避免把系统做得过于复杂。

### 乙：6. 统计与数据设计（约1分20秒）

【操作：我的→衣橱统计，切换月份，展示累计Top5和最近30天未穿】

统计分为几种不同口径：衣物总数和分类分布只统计未归档衣物；月度记录天数只看所选月份；常穿榜单按照累计日记次数排序；最近30天未穿也包含从来没有记录穿着的单品。

切换月份只改变月度天数，不会把累计榜单和最近30天窗口也切回历史月份。页面上的基准日期由服务器确定，所以历史样例的近期未穿结果会随着时间变化。

【可选操作：删除本次新日记前取消一次，再确认删除；重新进入统计观察变化】

修改或删除日记后，统计重新从数据库查询。我们不单独维护一份加减计数，避免日记和统计不同步。

数据结构一共七张表：用户、分类、衣物、搭配、搭配明细、日记和日记明细。两张明细表分别保存各自的衣物集合与顺序，这也是历史日记能保持独立的基础。

### 乙：7. 结束（约20秒）

我们的项目完成了从整理衣物、保存搭配，到记录穿着和回顾统计的主要流程。整体保留10个数据库业务页面，围绕日常使用控制功能范围，没有加入商城或AI推荐等额外模块。

以上是我们的展示，谢谢老师，欢迎提问。

## 四、老师追问时的简短回答

| 问题 | 建议回答 | 主答 |
| --- | --- | --- |
| 为什么搭配和日记需要两套明细？ | 搭配是可修改的组合方案，日记是某一天实际穿着；分别存才能避免修改搭配后历史跟着变。 | 乙 |
| 同一天重复记录怎么办？ | 唯一约束保证每人每天最多一篇，后端返回日期冲突，页面保留草稿并引导查看已有记录。 | 乙 |
| 穿着次数怎么算？ | 按包含该衣物的日记篇数计算，保存搭配不计次数；改记和删记后重新查询。 | 乙 |
| 为什么归档而不删除衣物？ | 归档能从默认列表隐藏，又不破坏过去的搭配和日记关联。 | 甲 |
| 图片为什么不直接存微信临时路径？ | 临时路径不是持久地址；上传到后端后保存本人目录中的稳定路径，读取时带登录身份。 | 甲 |
| 怎么防止读取别人的数据？ | 身份由登录认证确定，查询和写入限定当前user_id，保存关系再核对所选衣物的归属。 | 两人按模块补充 |
| AI参与了哪些工作？ | 我们使用Codex协助设计、代码、素材整理和自动检查；需求取舍、结果理解及展示由我们负责。具体个人操作和贡献按实际经历说明。 | 两人 |
| 测试和验收是否全部做完？ | 有已执行的自动、HTTP和数据库检查记录；剩余原生人工、截图等验收按我们的决定跳过，不能称全部实测通过。 | 乙 |
| 实际分工是什么？ | 本次展示甲负责账号/衣橱/搭配，乙负责日记/统计和数据关系；开发贡献另按真实记录说明。 | 两人 |

## 五、时间不足与现场异常

- 只有5分钟：甲讲背景20秒、衣橱1分钟、搭配1分钟；乙讲日记1分钟、历史独立/统计1分20秒、总结20秒。省略现场图片上传和照片分支，直接打开已有记录，不重复介绍表单所有字段。
- 图片暂时失败：保留页面实际提示并手动重试一次；不要说已成功上传或用无关图片替代。
- 服务未连接：说明本地后端连接异常，检查后端终端和接口地址；不反复点保存。若转静态原型，必须明确是原型，不能冒充真实数据库演示。
- 当天已有日记：用过去空日期或展示已有日记编辑，不能覆盖旧记录或改系统时间。
- 现场数据数量变化：以当前页面为准，不硬念24/8/12；原始演示数据数量可作为准备说明。
- 当前正式源码包不含运行数据库和uploads。换电脑前需按启动说明准备数据库与图片，不能仅解压源码就假定zyyuan的数据也已复制。
